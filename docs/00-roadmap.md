# ロードマップ

> Rebuild の最終ゴールと、そこまでの段階・完了条件・現在地をまとめた地図。
> 作業を始める前（人もAIも）に、このファイルで「今どの段階か」「次に何をするか」を確認する。
> 01〜05 の設計書は「何を作るか」、このファイルは「どの順番で、どこまでやれば完成か」を扱う。
> 作るもの（01・02）と、ゴールまでの道筋（このファイル）は、行き来しながら育てていく。

---

## 1. 最終ゴール

**個人開発で広告収入を得られるレベルのWebアプリとして公開し、運用・保守をしながら利用者の反応を見て改善を続けられる状態にする。**

| 優先順位 | ゴール | 判断に迷ったときの考え方 |
|---|---|---|
| ① | 公開：誰でも安心して使え、広告が表示され、運用できる | 利用者の安全・データの保護を最優先にする。費用は広告収入とのバランスで考える |
| ② | 学習：設計・実装・運用の判断を、理由とともに説明できる | 判断の理由は `docs/Study` に残す |
| ③ | ループ：AIが実装し、機械が検証する開発の流れを整える | ①②の作業を速く安全に進めるための手段として整える |

- 期間：2026年10月から半年〜1年（2027年4月〜10月）
- 判断ポイント：**2027年4月**に、正式リリースの見込みと、期限を延ばすかを判断する（[5章](#5-判断ポイント)）

## 3. 段階の詳細

各項目の印：✅ 完了 ／ 🔶 作業中・一部済み ／ ⬜ 未着手

### 段階0 プロダクトを固める

**なぜ最初か**：作るもの（利用者・画面・機能）にまだ考える余地が大きい。この状態で実装や認証を作り込むと、手戻りになる。要件と画面の流れを壁打ちで固めてから、実装に進む。

**決まったこと**（2026-10-14〜15。詳細は[要件定義](01-requirements/README.md)）

| 項目 | 内容 |
|---|---|
| 主な利用者 | 「絵を描けない原作者」と「自分でイラストを描く人」の両方を想定する。プロトタイプで反応を見て、どちらに寄せるかを決める |
| 一番の売り | 表現力と操作性：ストーリーの雰囲気が伝わるイラスト素材、自由なコマ割り、思い通りに配置できる漫画作成画面。PCで腰を据えて作業できること |
| 画面の流れ | 一覧はホームに集め、メニューは新規作成、新規と編集は同じ画面を使う。「メモ」は「アイデア帳」に改名。漫画作成の前のストーリー選択画面は廃止し、漫画作成画面の中で選ぶ。素材を探す・整理する素材画面を新設する |
| つながり | アイデア帳（複数）→ ストーリー（1つ）→ 漫画（複数）。1つのストーリーから何度でも漫画を作れる |
| 素材 | 雰囲気を揃えたイラスト素材を少数のまとまりから用意し、依頼・外部素材など複数の方法で集める。表情記号・効果線などはプログラムで描く。自分のイラストの取り込み（端末だけに保存も選べる）も残す。生成AIの素材はプロトタイプでは使わない |
| 吹き出し・コマ枠 | 素材ではなく機能として作る |
| 書き出し | 見開きPNG → PDF → 縦読みの順に対応する |
| ログイン前 | 全画面を見られる。漫画作成画面は操作でき、登録時に作ったものを引き継ぐ。見本データを用意する |
| 公開ページ・読み物 | トップ・使い方・見本の漫画に加え、ネームの作り方などの読み物を少しずつ書く（広告審査・集客のため） |
| 最初の利用者 | SNSで集める。リリースまでは読み物などで発信し、サイトのURLは段階1が終わるまで載せない |

| 状態 | 項目 |
|---|---|
| ✅ | 上の「決まったこと」を要件定義に反映する |
| ⬜ | 画面設計（`02`）に反映する：画面一覧の更新、新しい画面（素材・トップ・使い方・読み物・設定）の仕様書とワイヤーフレーム |
| ⬜ | 利用者が「これで作る」と判断する |

**完了条件**
- 決まったことが[要件定義](01-requirements/README.md)と[画面設計](02-screen-design/README.md)に反映されている
- 段階2の項目が、段階0の結果に合わせて書き直されている
- 利用者が「これで作る」と判断した

### 段階1 安全に公開できる状態にする

**なぜこの位置か**：今の本番では、ほかの利用者のメモ・ストーリーが見え、APIを直接呼べば読み書き・削除もできる。ただし、2026年10月時点で本番の登録者は開発者本人だけのため、急いで止める必要はない。認証の方式はログイン前のお試しの有無で変わるので、段階0の後に行う。他の人に使ってもらう段階3より前に、必ず終える。

| 状態 | 項目 | 関連資料 |
|---|---|---|
| ⬜ | メモに所有者（`user_id`）を追加し、自分のメモだけを扱う | [table-definitions.md](04-database/table-definitions.md) |
| ⬜ | すべてのAPIで、データの持ち主をサーバー側で判定する（他人のデータは拒否） | [api-list.md](05-api/api-list.md) |
| ⬜ | 認証（JWT）を導入し、ログイン前のお試しで使うもの以外のAPIを認証必須にする | [system-design.md 2章](03-system-design/system-design.md) |
| ⬜ | APIのパスを `/api/**` に統一する | [api-list.md](05-api/api-list.md) |
| ⬜ | 未テストのAPI（ストーリー/セリフ、ログイン/登録）のテストを追加する | [Study/05](Study/05-testing.md) |
| ⬜ | ブランチ保護を設定し、CIが失敗したらマージできないようにする | [Study/03](Study/03-loop-engineering.md) |
| ⬜ | 本番のバックエンドに反映し、本番でもデータが分離されていることを確認する | |

**完了条件**
- 別の利用者のデータを読む・変える・消すリクエストが拒否されることを、テストで確かめ、CIで通っている
- 認証が必要なAPIを、認証なしで呼ぶと拒否される
- 本番で、2つのアカウントのデータが互いに見えないことを確認した

### 段階2 プロトタイプを作る

**目的**：両方の利用者に共通する作業（ストーリー → ページ・コマ割り → 素材の配置 → セリフ → 書き出し）を、最後まで通して使える形にする。

| 状態 | 項目 | 関連資料 |
|---|---|---|
| ⬜ | DB・APIの設計を、段階0の結果に合わせて更新する（アイデア帳、入れ子のフォルダ、素材の出典・利用条件、漫画とストーリーのつながり、ページ管理など） | [04-database](04-database/README.md)、[05-api](05-api/README.md) |
| ⬜ | 画面の流れの作り直し：ホーム（一覧・「何から始めるか」）、アイデア帳への改名、新規と編集の画面の統一、ストーリー選択画面の廃止 | [02-screen-design](02-screen-design/README.md) |
| ⬜ | 素材画面（探す・見比べる・整理する・追加する。端末だけに保存も選べる） | [要件定義 REQ-009](01-requirements/README.md) |
| 🔶 | 漫画作成画面で自分の素材を使う（実装済み）に加え、ストーリーと素材フォルダを画面内で選ぶ | [CreateManga.md](02-screen-design/specifications/CreateManga.md) |
| ⬜ | 漫画のページ管理（ページの追加・削除・並び替え） | [manga.md](05-api/specifications/manga.md) |
| ⬜ | 自由なコマ枠と、枠による素材の切り取り | [要件定義 REQ-007](01-requirements/README.md) |
| ⬜ | 吹き出しとセリフの配置 | [dialogues.md](05-api/specifications/dialogues.md) |
| ⬜ | 素材の配置の操作性（拡大縮小・回転・反転・重ね順など） | |
| 🔶 | 見開きPNG書き出し（今は1ページのみ）と、書き出し画質の改善 | [system-design.md 5章](03-system-design/system-design.md) |
| ⬜ | 最初のイラスト素材を用意する（雰囲気を揃えた少数のまとまり。出典・利用条件を記録する） | |
| ⬜ | 見本データ（アイデア帳・ストーリー・漫画）と、ログイン前の体験 | [要件定義 REQ-010・011](01-requirements/README.md) |
| ⬜ | 公開ページ（トップ・使い方・見本の漫画）と、最初の読み物 | [要件定義 REQ-012](01-requirements/README.md) |
| ⬜ | 利用者の一連の流れの確認手順を `06-test` に書く | [06-test](06-test/README.md) |

**完了条件**
- 新しい利用者が、ログイン前の体験（または登録）→ ストーリー → ページ・コマ割り → 素材の配置 → セリフ → 書き出し、まで迷わずに一通りできる（`06-test` の確認手順に沿って確認）
- 画面仕様書に「別途確定する」が残っていない（残す場合は範囲外と明記する）

### 段階3 限定公開で反応を見る

**目的**：少人数に使ってもらい、どちらの利用者に、どの機能が求められているかを確かめる。

| 状態 | 項目 |
|---|---|
| ⬜ | SNSでの発信（読み物・漫画原作の考え方など）を、段階2の間から続ける |
| ⬜ | アクセス解析を導入する（どの機能がどれだけ使われたかを数字で見る） |
| ⬜ | 感想・要望を集める手段を用意する |
| ⬜ | 少人数に使ってもらい、反応をまとめる |
| ⬜ | 反応をもとに、段階5までの項目と優先順位を見直す（生成AIの素材を使うかもここで判断する） |

**完了条件**：開発者以外の利用者が実際に使い、その反応から次に直すこと・足すことを決めた。

### 段階4 運用の土台を作る

**目的**：公開後に、データを失わず、安全に修正を出し続けられるようにする。

| 状態 | 項目 | 関連資料 |
|---|---|---|
| ✅ | フロントエンドの自動テスト・自動デプロイ（S3 + CloudFront） | [Study/04](Study/04-ci-github-actions.md) |
| ✅ | バックエンドの自動テスト（CI） | [Study/04](Study/04-ci-github-actions.md) |
| ⬜ | バックエンドの自動デプロイ（今はEC2へ手動で反映） | |
| ⬜ | DBの構造変更を管理する仕組み（今は起動時の自動更新に任せている） | [table-definitions.md](04-database/table-definitions.md) |
| ⬜ | アップロード画像をS3へ移す（今はEC2のディスクにあり、EC2が失われると消える） | [system-design.md 3章](03-system-design/system-design.md) |
| ⬜ | DBのバックアップと、そこから戻す手順の確認 | |
| ⬜ | 監視・ログ（障害に気づける状態） | [tech-stack.md](03-system-design/tech-stack.md) |
| ⬜ | EC2のOS更新 | |
| ⬜ | 本番構成の判断：ECS へ移行するか、EC2 のまま続けるか（[4章](#4-本番構成の方針)） | [system-architecture.md](03-system-design/system-architecture/system-architecture.md) |

**完了条件**
- main へのマージで、フロントとバックエンドの両方が自動で本番に反映される
- 本番のDBとアップロード画像が失われても、バックアップから戻せることを一度試した
- 本番の障害（停止・エラーの増加）に、利用者からの連絡より先に気づける

### 段階5 正式リリース

**目的**：限定公開から、誰でも使える公開に切り替え、広告を表示する。

| 状態 | 項目 | 関連資料 |
|---|---|---|
| ⬜ | 招待コードを廃止し、誰でも登録できるようにする | [system-design.md 4章](03-system-design/system-design.md) |
| ⬜ | 利用規約・プライバシーポリシー・問い合わせ先を用意する | [要件定義 7章](01-requirements/README.md) |
| ⬜ | 広告サービスに申請し、審査に通す（広告は編集中の作業を邪魔しない画面に置く） | [要件定義 6章](01-requirements/README.md) |

**完了条件**
- 招待コードなしで誰でも登録でき、規約に同意して使い始められる
- 広告が本番で表示されている

### 段階6 運用・改善

**目的**：利用者の反応を見て改善し、それを繰り返せる状態を保つ。

| 状態 | 項目 |
|---|---|
| ⬜ | 利用者の反応（アクセス解析・感想）から改善点を選び、改善を出す |
| ⬜ | 障害・不具合の対応と、その記録 |
| ⬜ | 素材のまとまりと書き出しの形式を、反応を見て増やす |

**完了条件**：改善を1回以上、「反応を見る → 直す → 結果を確かめる」の流れで行った。

## 4. 本番構成の方針

最終的な構成は ECS（[system-architecture.md](03-system-design/system-architecture/system-architecture.md)）を目標とする。ただし、ECS 構成は常時かかる費用（ロードバランサ・DB・ネットワーク）が今の EC2 より大きいため、移行の時期は段階4の中で判断する。

| 判断材料 | 確認すること |
|---|---|
| 費用 | 月々の費用の差と、広告収入の見込み |
| 必要性 | 利用者数・負荷に対して、今の EC2 で足りているか |
| 学習 | 構成を自分で説明できる状態にしたいか |

それまでは EC2 のまま、自動デプロイ・バックアップ・監視を整える。判断の結果と理由は `docs/Study/02-design-decisions.md` に残す。

## 6. このファイルの使い方

- 作業を始める前に、今の段階と次の項目を確認する。AIは、ここから次の一手を提案する
- 優先順位は「段階の順番 → 段階の中では上の項目から」を基本とする。順番を変える場合は理由を伝える
- 項目が終わったら印を更新する（完了かどうかは、利用者が確認してから ✅ にする）
- 新しい課題が見つかったら、どの段階に入れるかを決めて追加する
