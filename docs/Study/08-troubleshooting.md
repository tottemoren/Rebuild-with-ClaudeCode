## 1. 自動デプロイで認証エラー（OIDC）

- **症状**：GitHub ActionsからAWSへの認証で、`Not authorized to perform sts:AssumeRoleWithWebIdentity` が出る。
- **原因**：特定できていません。信頼ポリシー、プロバイダー設定、ワークフロー、リポジトリ設定をすべて確認し、作り直しても同じエラーでした。
- **対処**：原因の究明をいったん保留し、アクセスキー方式（キーはGitHubのSecretsに保存、権限は必要なS3とCloudFrontに限定）に切り替えて、デプロイを完成させました。
- **学び**：**完璧な方式にこだわって止まるより、動く形を先に作り、残課題を記録する**。アクセスキーは長期間有効なので、定期的な入れ替えが必要です（残課題）。

## 2. EC2にSSHで接続できない

- **症状**：接続がタイムアウトする。
- **原因**：セキュリティグループのSSHルールが「自分のIPだけ許可」になっており、作業場所（Wi-Fi）を変えたことでIPが変わり、古いIPのままだった。
- **対処**：ルールのIPを、現在のものに設定し直した。
- **学び**：**接続できないときは、アプリより先にネットワークの許可設定を疑う**。IPが変わる環境では、この問題が繰り返し起こります。

<sub>作業記録：[2026-09-29](../docs/ClaudeCode%20CHANGELOG/2026/09/2026-09-29.md)</sub>

## 3. アップロードした画像が消える

- **症状**：アップロードした素材のDBレコードは残っているのに、ファイルが存在しない。
- **原因**：Dockerのバックエンド用コンテナに、保存先のボリューム設定がなく、ファイルがコンテナの中にしか存在しなかった。コンテナを作り直すと消える。
- **対処**：`compose.yml` に `./RebuildJava/uploads:/app/uploads` を1行追加して、パソコン側のフォルダと紐づけた。コンテナを作り直しても、ファイルが残ることを確認した。
- **学び**：**コンテナの中は、使い捨て**。残したいデータは、ボリュームで外に出す。

<sub>作業記録：[2026-08-18](../docs/ClaudeCode%20CHANGELOG/2026/08/2026-08-18.md)</sub>

## 4. 変更が反映されない・通信エラー

- **症状**：コードを直したのに画面が変わらない。または、別のポートで開いたら通信エラーになった。
- **原因**：
  - Dockerのイメージが古く、新しいコードが入っていなかった。
  - 別のポート（5174）で開発サーバーを動かしたため、バックエンドのCORS許可（許可するアクセス元）に含まれていなかった。
- **対処**：イメージを再ビルドする（`docker compose up -d --build`）。許可されているポート（5173）で開く。
- **学び**：**「コードが正しいのに動かない」ときは、環境（古いイメージ・ポート・許可設定）を疑う**。

<sub>作業記録：[2026-08-18](../docs/ClaudeCode%20CHANGELOG/2026/08/2026-08-18.md)</sub>

## 5. 開発サーバーが `ENOENT` で止まる

- **症状**：ファイルの短時間の連続編集のあと、Vite（開発サーバー）が `ENOENT` で停止した。
- **原因**：Docker Desktopのファイル監視が、パソコンとコンテナの間の同期のタイミングで、まれに不整合を起こす。コード自体の問題ではなかった。
- **対処**：`docker compose restart frontend` で復旧。
- **学び**：エラーが出ても、コードの問題とは限りません。**再起動で直るかを、早めに試す**。
- **再発（10月12日）**：AIがファイルを書き換えた瞬間に、開発サーバーがそのファイルを読みにいき、`ENOENT` でコンテナごと停止した。エディタの保存は「新しいファイルを作って入れ替える」方式のことがあり、その一瞬だけファイルが存在しないため。`docker start rebuild-react` で復旧し、以後はファイルを**その場で上書きする**方法に変えて、再発しなくなった。

## 6. ヘッダーが縦に異常に長くなる

- **症状**：画面のヘッダーが、縦に900px近くまで引き伸ばされた。
- **原因**：次の2つが重なっていました。
  - 画像に `height: 90%` を指定していたが、基準になる親要素の高さが決まっておらず、画像が元のサイズで表示された。
  - 横並び（flex）の `align-items: stretch` により、隣の要素まで引き伸ばされた。
- **対処**：画像の高さを、固定のpx指定に変更。あわせて、折り返しや余白を詰めた。
- **学び**：**`%` の高さは、親の高さが決まっていて、はじめて意味を持つ**。レイアウトの統合のような大きな整理のあとは、全画面の見た目を確認する。

<sub>作業記録：[2026-10-01（ヘッダーの高さ崩れ）](../docs/ClaudeCode%20CHANGELOG/2026/10/2026-10-01-createmanga-header-fix.md)</sub>

## 7. ローカルで `./gradlew test` が失敗する

- **症状**：DBなしで実行すると、`contextLoads` が失敗する。
- **原因**：Spring Bootの起動時にDBへ接続しようとするが、設定の接続先 `mysql:3306` は、Docker内でしか通じない。
- **対処**：別のポートに使い捨てのMySQLを立て、環境変数で接続先を上書きする（[04. CIとGitHub Actions](04-ci-github-actions.md)参照）。
- **学び**：テストが失敗した原因が、コードではなく**環境**ということもある。CIにMySQLが必要な理由も、これで確認できた。

<sub>作業記録：[2026-10-05](../docs/ClaudeCode%20CHANGELOG/2026/10/2026-10-05.md)</sub>

## 8. `@AutoConfigureMockMvc` が見つからない

- **症状**：テストのコンパイルが通らない。
- **原因**：Spring Boot 4 で、テスト用の部品が別のパッケージ・別の依存に分かれた。
- **対処**：`spring-boot-starter-webmvc-test` を追加し、`org.springframework.boot.webmvc.test.autoconfigure` からインポートする。
- **学び**：**バージョンが新しいと、以前の情報が通用しない**ことがある（[05. テストの考え方](05-testing.md)参照）。

## 9. 暗号化の導入後、ログインできない

- **症状**：パスワードの暗号化（BCrypt）を導入したあと、以前から登録済みのユーザーがログインできない。
- **原因**：保存されているパスワードが、暗号化されていない文字列のままだったため、照合の方式と合わなくなった。
- **対処**：テスト用アカウントを、再登録する。
- **学び**：**仕様の変更は、既存のデータにも影響する**。導入前に、影響を確認しておく。

## 10. 2:1固定をやめたら、黒い帯が見えるようになった

- **症状**：画面全体を「横2：縦1」の枠に固定するのをやめたところ、ストーリー創作画面の左下に黒い帯が出た。
- **原因**：画面の外枠の背景が、もともと黒に指定されていた。さらに、中の要素の高さの合計が外枠を超えていた。これまでは2:1の枠で切り取られて見えていなかっただけだった。
- **対処**：外枠の背景を白（デザイントークン）にし、中身が多いときは列の中でスクロールするようにした。
- **学び**：**大きな枠を変えると、隠れていた古い問題が表に出る**。全体のレイアウトを変えたら、全画面を見て確かめる。

## 11. コマ配置の読み込みが500エラー（`ZIndex` が見つからない）

- **症状**：漫画作成画面を開くと「コマ配置の読み込みに失敗しました」。APIが `500` を返す。ログには `Could not resolve attribute 'ZIndex'`。
- **原因**：Spring Data の「メソッド名から検索を自動で作る」仕組み（派生クエリ）で、`findByStoryIdOrderByZIndexAsc` の `ZIndex` を、項目名 `ZIndex` と解釈した。実際の項目名は `zIndex`（先頭が小文字）だった。
- **対処**：検索の内容を `@Query` で明示した（「ストーリーIDで絞り、`zIndex` の小さい順」）。
- **学び**：**名前から自動で作る仕組みは便利だが、`zIndex` や `xPos` のように「小文字1文字＋大文字」で始まる名前は、解釈がずれやすい**。迷ったら明示的に書く。

<sub>作業記録：[2026-10-13（3回目）](../docs/ClaudeCode%20CHANGELOG/2026/10/2026-10-13.md)</sub>

## 12. 2回目以降の「サーバーに保存」が失敗する

- **症状**：一度保存したあとで、もう一度「サーバーに保存」すると失敗する。
- **原因**：保存処理は「古い配置を削除してから、新しい配置を保存する」作りだった。この種の削除は、処理をひとまとまりにする設定（トランザクション、`@Transactional`）がないと実行できず、`TransactionRequiredException` になっていた。最初の保存は、削除するものがないので通っていた。
- **対処**：保存処理に `@Transactional` を付けた。削除と保存がひとまとまりになり、途中で失敗したときに中途半端な状態も残らない。
- **学び**：**「削除してから入れ直す」処理は、ひとまとまり（トランザクション）にする**。また、この不具合は既存のテストの書き方では見つけられなかった（[05. テストの考え方](05-testing.md)の「`@Transactional` がテストの見落としを生む」を参照）。

<sub>作業記録：[2026-10-13（3回目）](../docs/ClaudeCode%20CHANGELOG/2026/10/2026-10-13.md)</sub>

## 13. 「画像として保存」で `SecurityError` になる

- **症状**：アップロードした素材を配置したページを「画像として保存」すると、失敗する。
- **原因**：書き出しは、ブラウザの中のキャンバスに画像を描いてPNGに変換する。別のオリジン（バックエンドの `localhost:8080`）の画像を、許可なく描いたキャンバスは「汚染された」扱いになり、ブラウザがPNGへの変換を禁止する。許可には、①画像を「許可を求める読み込み方」（`crossOrigin = "anonymous"`）で読み、②配信側が許可の返事（CORSのヘッダー）を付ける、の両方が必要だった。
- **対処**：書き出し用の画像を `crossOrigin = "anonymous"` で読み込み、バックエンドで `/uploads/**` の読み込み（GETのみ）を、フロントエンドの配信元に限って許可した。
- **学び**：**画像を「表示する」だけなら許可は不要だが、「キャンバスで加工する」には許可が必要**。原因を確かめるときは、ブラウザ内で「許可なし／許可あり」の2通りを試すと、違いがはっきり分かる。

<sub>作業記録：[2026-10-13（4回目）](../docs/ClaudeCode%20CHANGELOG/2026/10/2026-10-13.md)</sub>

## 14. 本番だけ、画像のアップロードが失敗する（`403`）

- **症状**：ローカルでは成功するのに、本番ではアップロードが失敗する。画面にはエラーが出ない（失敗を表示しない作りだった）。
- **調べ方**：
  1. EC2のログにエラーがなく、保存先フォルダも作られていない → **リクエストがEC2に届いていない**
  2. ブラウザの開発者ツールの Network で、API用の CloudFront が `403` を返しているのを確認。Console の「CORSでブロック」は、拒否の返事に許可の情報が付いていなかったための**二次的な表示**だった
  3. 存在しない住所に、1KB と 20KB のデータを送って比べた → 1KBは `404`（EC2まで届く）、20KBは `403`（途中で拒否）。**データを変えずに**原因を切り分けられた
- **原因**：API用 CloudFront の WAF（標準ルール）の `SizeRestrictions_BODY` が、8KBを超える送信をブロックしていた。ローカルにはCloudFrontもWAFもないので、本番だけで起きた。
- **対処**：CloudFront の無料プランでは「アップロードの窓口だけ除外する」ルール（ラベルを使う方法）が作れなかったため、`SizeRestrictions_BODY` を「カウント（記録だけ）」に変えた。他の標準ルールはそのまま。長いメモやストーリーの保存も、同じ理由で止まっていたはず。
- **学び**：**ローカルで動いて本番で動かないときは、間にある仕組み（CloudFront・WAF・ロードバランサーなど）を疑う**。調べる順番は「サーバーに届いているか → どこで止まっているか → 何が条件か」。無料プランには制限があるので、理想の設定ができないときの次善策と、その影響（ここでは大きなデータを全体で止めなくなる）を記録しておく。将来は、画像をS3へ直接アップロードする方式に移すと、この問題自体がなくなる。

<sub>作業記録：[2026-10-13（5回目）](../docs/ClaudeCode%20CHANGELOG/2026/10/2026-10-13.md)</sub>

## 15. EC2へのSSHで `Permission denied (publickey)`

- **症状**：`ssh -i 鍵ファイル ec2-user@…` で接続すると、拒否される。
- **原因**：EC2のOSが Ubuntu だったため、ユーザー名は `ec2-user`（Amazon Linux 用）ではなく `ubuntu` だった。
- **対処**：`ubuntu@…` で接続できた。
- **学び**：**「タイムアウト」はネットワーク（セキュリティグループ）の問題、「Permission denied」はサーバーまでは届いていて、ログインの段階（ユーザー名・鍵）の問題**。エラーの種類で、調べる場所を切り分けられる。

<sub>作業記録：[2026-10-13（5回目）](../docs/ClaudeCode%20CHANGELOG/2026/10/2026-10-13.md)</sub>

## 16. 並行で作ったPRが、CHANGELOG でコンフリクトした

- **症状**：PR #20 に「This branch has conflicts that must be resolved」と表示され、マージできない。対象は `docs/docs/ClaudeCode CHANGELOG/2026/10/2026-10-15.md`。
- **原因**：2つのPR（#19 と #20）を、**同じ時点の main から**作り、どちらも同じ日の CHANGELOG の**一番最後に**追記していた。先に #19 がマージされたため、#20 は「同じ場所に別の内容を書き足す」状態になった。内容そのものはぶつかっていない。
- **対処**：GitHub の画面（Resolve conflicts）で、`<<<<<<<`・`=======`・`>>>>>>>` の印の行だけを消し、「4回目」→「5回目」の順に両方の記録を残して、マージを確定した。
- **学び**：**コンフリクトは「同じファイルの同じ場所」を別々に変えると起きる**。中身が両立するなら、両方を残せばよい。防ぐには、同じファイルに追記するPRは、前のPRがマージされてから次のブランチを作る（または、追記をPRの最後に回す）。

<sub>作業記録：[2026-10-15（5回目・6回目）](../docs/ClaudeCode%20CHANGELOG/2026/10/2026-10-15.md)</sub>
