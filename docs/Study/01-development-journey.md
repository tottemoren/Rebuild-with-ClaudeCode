# 01. 開発の歩み

8月〜10月に何をどの順で進めたかを、「そのときの考え方」と一緒に整理します。日々の詳細は [CHANGELOG](../docs/ClaudeCode%20CHANGELOG/) にあります。

## 全体の流れ

| 時期 | 段階 | やったこと |
|---|---|---|
| 8月上旬 | 機能の土台 | ログインのパスワード暗号化（BCrypt）、プロフィール画像、漫画作成画面、画像として保存する機能 |
| 8月中旬 | 設計書を整える | 要件・画面・システム・DB・APIの設計書（`docs/01〜05`）を作成 |
| 8月下旬〜9月 | 本番公開の準備 | APIの接続先を環境変数化、GitHub ActionsでフロントをS3 + CloudFrontへ自動デプロイ、独自ドメインとSSL |
| 9月下旬 | 画面の整理 | ヘッダーとレイアウトの重複を統合（設計書のワイヤーフレームに合わせる） |
| 10月 | 検証の仕組みを作る | バックエンドCI、APIテスト、CLAUDE.mdの見直し |

## 段階ごとの考え方

### 1. 機能の土台（8月上旬）

**やったこと**：パスワードをそのまま保存せず、BCryptで暗号化（ハッシュ化）して保存するようにしました。画面では、ドラッグでコマ画像を配置し、枠内をPNGとして保存できるようにしました。

**考え方**：個人情報（パスワード）の扱いは、後から直すほど影響が大きくなります。そのため機能が少ない早い段階で入れました。

**学んだこと**：保存方法を変えると、既存のデータが使えなくなることがあります。平文で保存済みのユーザーは、ハッシュ化後はログインできなくなるため、再登録が必要でした。**仕様変更は、既存データへの影響まで考える**必要があります。

### 2. 設計書を整える（8月中旬）

**やったこと**：画面のワイヤーフレームから画面仕様書を作り、要件定義、システム設計、データベース設計、API設計へと広げました。

**考え方**：コードを書く前に「何を作るか」を言葉と図にしておくと、AIに指示するときも、自分で見直すときも、判断の基準になります。

**学んだこと**：設計書を書く過程で、コードだけを見ていたときには気づかなかった問題が見つかりました（例：メモに `user_id` がなく、全ユーザーで共有されてしまう）。**設計書は、問題を見つける道具にもなります**。詳しくは [02. 設計判断と理由](02-design-decisions.md) を参照してください。

### 3. 本番公開の準備（8月下旬〜9月）

**やったこと**：
- ソースコードに直接書いていた `http://localhost:8080`（26か所）を、環境変数（`VITE_API_BASE_URL`）に置き換えました。
- フロントエンドを、S3 + CloudFrontへ自動デプロイするワークフローを作りました。
- 独自ドメインを取得し、SSL証明書を設定しました。

**考え方**：接続先をコードに直接書くと、環境ごとに書き換える手間と間違いが生まれます。環境変数にすれば、開発用と本番用を同じコードで切り替えられます。

**学んだこと**：自動デプロイの認証で、推奨されるOIDC方式が原因不明のまま失敗し、アクセスキー方式に切り替えました。**完璧を求めて止まるより、動く形を先に作り、残った課題を記録する**という判断をしました。詳しくは [08. つまずきと解決](08-troubleshooting.md) を参照してください。

### 4. 画面の整理（9月下旬）

**やったこと**：似た役割のヘッダーやレイアウトのファイルを、1つにまとめました（`Header` と `MainLayout` に統合）。広告枠の有無は、`showAdvertisement` という設定値で切り替える形にしました。

**考え方**：ほぼ同じ内容のファイルが複数あると、片方だけ直して食い違いが生まれます。違いが「設定値で表せる程度」なら、1つにまとめるほうが安全です。

**学んだこと**：まとめる作業の途中で、レイアウトの高さが崩れる不具合が出ました（高さの基準になる親要素に高さを指定し忘れていた）。**大きな整理は、見た目の確認と、小さな段階ごとの確認が欠かせません**。

### 5. 検証の仕組みを作る（10月）

**やったこと**：バックエンドのCIを追加し、メモとフォルダ/素材のAPIテストを書き、CLAUDE.mdを見直しました。

**考え方**：AIに実装を任せる量が増えるほど、「正しく動いているか」を人間が毎回目で確認するのは現実的でなくなります。**機械が自動で検証する仕組み**を先に作りました。

**学んだこと**：次の3つです。詳しくは各ノートを参照してください。
- 「テストがある」だけでは足りず、**壊れたときに本当に失敗するか**の確認が必要（[05](05-testing.md)）
- AIには**守らせるルールを文章で渡す**だけでなく、**機械で止める仕組み**も必要（[07](07-working-with-ai.md)）
- この流れ全体は、[03. ループエンジニアリング](03-loop-engineering.md) の考え方に沿っています
