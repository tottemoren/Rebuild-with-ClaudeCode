# 07. AIと開発する工夫

AI（Claude Code）に開発を任せるときに、うまくいったこと・失敗したこと・対策を整理します。

## 基本の考え方

- **決めるのは人間、作業するのはAI**：目標・方針・マージなどの最終判断は人間が持つ
- **AIの言うことを、そのまま信じない**：テストや実際の動作で確かめる
- **AIに渡す情報を、設計する**：必要な情報を、必要なときに読める形で置いておく

## AI向けドキュメントの3層

| 層 | 役割 | Rebuildでの例 |
|---|---|---|
| ① 入口 | 毎回必ず読む、短いルールと地図 | [CLAUDE.md](../../CLAUDE.md) |
| ② 仕様の正本 | 作るものの詳細。必要なときに読みにいく | `docs/01〜05`（要件・画面・設計・DB・API） |
| ③ 手順と強制 | 繰り返す作業の手順、機械的なチェック | CI（導入済み）。Hooks・ブランチ保護などは今後 |

**なぜ分けるのか**：入口に何でも書くと、長くなって、大事なルールが埋もれます。入口は短く、詳細は別の文書へ案内する形が適しています。

## CLAUDE.mdに書いたこと

CLAUDE.mdは、AIがこのリポジトリで作業するたびに読み込む決まりごとです。2026年10月に、「AIの暴走を防ぐ」ことを最優先に見直しました。

| 項目 | 内容 |
|---|---|
| 作業の進め方 | 変更の前に、目的・考え方・作業予定・リスクを説明して、了解を得る。1ステップずつ進める |
| 事前確認が必要な操作 | gitの履歴操作、削除、GitHub/AWSの設定変更、鍵の扱い、`.github/workflows/` の変更、依存の追加、認証・CORS・DB接続の変更 |
| 検証の義務 | テストとlintを実行して結果を報告する。テストを弱めて通すことは禁止 |
| 範囲の守り方 | 依頼されていない修正はしない（気づいたら報告のみ）。1PR1目的 |
| プロジェクトの注意 | 実データのフォルダを消さない。実在の人物・作品の名前や画像を使わない |

## 実際に起きた失敗と対策

AIとの作業で、次のような失敗がありました。**失敗を記録し、ルールや確認の仕組みに変える**ことが、品質を上げます。

| 失敗 | 原因 | 対策 |
|---|---|---|
| 日付を1日間違えて、18ファイルに書いた | 実際の日付を確認せずに書いた | 利用者の指摘で一括修正。日付は、実際の値を確認してから書く |
| 作業中に、必要なファイルを誤って削除した | 新しいファイルの名前が、古いファイルと同じだった | バックアップ（作業用の一時ファイル）から復旧。上書きの前に、対象を確認する |
| 動作確認をせずに「できた」と思ってしまった | 初期の作業環境が外部ネットワークを使えず、ビルドや起動ができなかった | 確認できなかったことを明記し、手元での確認手順を提示した。以後は「確認した／していない」を区別して報告する |
| 止めたはずのサーバーが動き続けていた | 停止の指定が、実際の起動コマンドと一致していなかった | プロセスを特定して停止。「止めた」ではなく、「止まったこと」を確認する |
| 実在の人物・作品の名前や画像が混入していた | 素材の名前が、実在のものと一致していた | 架空の名前と、自作の画像に差し替え。素材を追加するときは、実在のものと一致していないか確認する |
| 「本番にバックエンドはない」と思い込み、PRの本番への影響を誤って説明した | AIが毎回読む CLAUDE.md の記述が古く、実態（EC2で手動運用）と違っていた。10月6日の記録に「ずれている可能性」が指摘されていたのに、直されないままだった | 利用者の指摘で記録を確認し、CLAUDE.md を実態に合わせた（2026-10-13）。**AIは、入口の文書が古いと、自信を持って間違える**。ずれに気づいたら、後回しにせず直す |

## 「お願い」と「強制」の違い

CLAUDE.mdの文章は、AIへの**お願い**です。守られることが多いですが、**絶対ではありません**。

| 種類 | 例 | 強さ |
|---|---|---|
| お願い（文章） | CLAUDE.mdのルール | 弱い（守られない可能性がある） |
| 検証（機械） | テスト、lint、CI | 強い（失敗したら分かる） |
| 強制（仕組み） | ブランチ保護、Hooks、権限の制限 | 最も強い（そもそもできない） |

大事なルールほど、文章だけに頼らず、**仕組みで止める**方向に移していくのが理想です。

**実際に仕組みが働いた例**：CIの設定ファイル（`.github/workflows/`）を変更するPRで、利用者の了承を得たうえで、AIがコミットしようとしたところ、AIの操作を見張る自動判定に止められました（理由は「CIの回避」）。CIの設定は検証の仕組みそのものなので、AIが勝手に変えると、検証を弱めることもできてしまうからです。AIは止められた操作を回避せず、変更内容を説明して、コミットと push を利用者が行いました。少し手間は増えますが、**検証の仕組みを変える操作は人間が最後に手を動かす**という分担は、ループエンジニアリングの「自動化が自動化を壊す」落とし穴（[03](03-loop-engineering.md)）への対策そのものです。

## AIにゴールの地図を渡す

**気づいたこと**：それまでは、「次に何をするか」を毎回人間が考えてAIに指示していました。そのため、順番や優先順位が場当たり的になりがちでした。設計書（`docs/01〜05`）を揃えていても、AIに「最終的なゴールは読み取れるか」と聞くと、答えは「半分」でした。**何を作るか**は書かれていましたが、**どこまでできたら完成か**と**どの順番で進めるか**は、どこにも書かれていなかったからです。

**やったこと**：最終ゴール、優先順位、段階ごとの完了条件と現在地を、1枚の地図（[00-roadmap.md](../00-roadmap.md)）にまとめました。CLAUDE.md からこの地図へ案内し、AIが作業を提案する前に読むようにしました。

**考え方**：

| 人間が持つもの | AIに任せられるもの |
|---|---|
| ゴールと優先順位を決める、完了を判断する | 地図と現在地から、次の一手を提案する |

- 完了条件がなければ、AIもテストも「できた」を判断できません。地図は、[03. ループエンジニアリング](03-loop-engineering.md)の「① 目標・合格条件」の部品にあたります
- 地図は一度で完成させるものではありません。作るもの（要件）と、ゴールまでの道筋（地図）を、行き来しながら育てていきます

## 定期的に批評と提案をもらう

**きっかけ**：自分とAIだけで考えていると、判断が偏ったり、作りたい機能が増えすぎたりします。利用者のアイデアで、**定期的に外からの目で見てもらう仕組み**を作りました。

| | 批評エージェント | アドバイスエージェント |
|---|---|---|
| 役割 | 守り：今の計画・成果物の問題点を指摘する | 攻め：新しい技術・AIの使い方を調べて提案する |
| 頻度 | 毎週月曜 | 月2回（第1・第3木曜） |
| 読むもの | ロードマップ、変更履歴、非公開のメモ、過去のレビュー | Webの最近1〜2か月の情報、ロードマップ、過去の提案 |
| 出すもの | 厳しい指摘3つ＋良かった点1つ＋次の一手1つ（毎回観点を変える） | 最大3つの提案（効果・手間・判断の案・出典つき） |

**設計で工夫したこと**：
- **AIは実行のたびに学習しない**ので、そのままでは同じ種類の的外れな指摘を繰り返します。利用者が「役に立った／的外れ」を**反応のメモ**に書き、両エージェントが毎回それを読むことで、材料が育って精度が上がる形にしました（ループエンジニアリングと同じ考え方です）
- **機能が増えすぎないように**：指摘・提案は「提案まで」。新しい機能を足す提案には、ロードマップのどの段階に入れるかと、今の段階を遅らせないかを必ず書かせます。採用するかは利用者が決めます
- **見落とさないように**：結果を開かないと忘れてしまうため、会話の始めにAIが未確認の批評・提案を伝え、感想を聞くようにしました
- **権限は読むことだけ**：エージェントはリポジトリを変更せず、結果のファイルを1つ書くだけです

## AIに任せるときの注意

- **権限は最小限に**：AIに本番環境を直接変更させず、デプロイはCIに任せる
- **鍵・パスワードは渡さない**：チャットに貼らない。ファイルに書かない
- **自動化の設定は、人間が確認する**：`.github/workflows/` は、本番公開に直結するため
- **「できた」の報告を疑う**：実装できたと言われても、完成していないことがある。ドキュメントや進捗の更新は、完成を確認してから行う
- **AIの調査は、読み取りだけから始める**：状態を確認してから、変更の作業予定を立てる
- **記録を実態に合わせ続ける**：AIは記録を前提に判断する。本番構成などが変わったら、CLAUDE.md も同じPRで直す

## 動作確認でデータに触れるとき

AIに画面の確認を任せるとき、次のように決めて進めました。

| 場面 | やり方 |
|---|---|
| ログインが必要な画面を見る | パスワードは使わず、ブラウザに**存在しないダミーユーザー**を入れて表示し、終わったら消す |
| 実際のデータで確かめたい | 「開発用DBのユーザーとして見る」ことを、**事前に了承をもらう**。データは変えない |
| 保存ボタンを試したい | 書き込む内容と、**元に戻す方法**を説明して了承をもらう。確認後に元に戻し、戻ったことも確かめる |
| 削除・ダウンロードのボタン | 押さない（必要なら了承を取る）。代わりに、ブラウザの中だけで仕組みを確かめる |
| 本番の原因を調べる | **データを変えない方法**を選ぶ（例：存在しない住所にデータを送って、大きさによる違いを見る） |
| 本番のサーバーやAWSの設定 | AIは手順を説明し、操作は利用者が行う |
