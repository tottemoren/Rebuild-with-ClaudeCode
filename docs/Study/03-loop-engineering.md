# 03. ループエンジニアリング

## ひとことで言うと

**AIが実装し、機械が検証し、失敗したらAIが直す。この繰り返し（ループ）を回し、人間は「目標を決める」と「最後に判断する」に集中する**開発スタイルです。

```
目標・合格条件を決める（人間）
        ↓
   AIが実装する
        ↓
 機械が検証する（テスト・lint・CI）
        ↓
  失敗 → AIが直す（ループ） ／ 成功 → 人間が最終判断
```

## なぜ必要なのか

AIに任せる量が増えるほど、人間が毎回すべてのコードを目で確認するのは、現実的ではなくなります。その代わりに、「正しく動いているか」を**機械が自動で判定する仕組み**があれば、人間は大事な判断に時間を使えます。

つまり、AIの速さを活かすには、**検証の仕組みを先に整える**必要があります。このプロジェクトで、先にCIとテストを整えたのはそのためです。

## ループの部品

ループが回るには、次の5つが必要です。

| 部品 | 意味 | Rebuildでの例 |
|---|---|---|
| ① 目標・合格条件 | 何をもって「できた」とするか | 画面仕様書、APIの仕様（受け入れ条件は今後整備） |
| ② 検証の信号 | 合格かどうかを機械が判定する | テスト、lint、CI（緑／赤） |
| ③ 実行役 | 実際に作業する | Claude Code |
| ④ 止める条件 | 繰り返しを終える基準 | CIが全部緑、人間がマージを決める |
| ⑤ 人間への引き継ぎ | 迷ったら人間に聞く | CLAUDE.mdの「事前確認が必要な操作」 |

## 3つのループの層

| 層 | 内容 | 速さ |
|---|---|---|
| 内側のループ | 書いたらすぐ、lint・テストを回す | 数秒〜数分 |
| 真ん中のループ | PRを出す → CIが検証 → レビュー → 直す | 数分〜数時間 |
| 外側のループ | 本番の監視 → 問題を検知 → 修正のPRを作る | 日単位 |

## 落とし穴

| 落とし穴 | 説明 | 対策の例 |
|---|---|---|
| テストを弱める | AIがテストを通すために、テストの方を書き換えてしまう | 「テストを弱めて通すことの禁止」をルール化。テストファイルの変更を人間が確認する |
| 終わらない・費用がかさむ | 直しては失敗する繰り返しが止まらない | 回数や時間の上限を決める |
| 間違った方向に収束する | 検証が甘いと、「緑だが間違っている」状態になる | 検証の質を確認する（[05. テストの考え方](05-testing.md)の「テストのテスト」） |
| 自動化が自動化を壊す | ワークフローや権限をAIが勝手に変える | `.github/workflows/` の変更は、事前確認を必須にする |
| 権限を与えすぎる | AIが本番を変更できてしまう | 最小権限にする（デプロイはCIだけが行う） |

**次に進めること**：検証の範囲を広げること（ストーリー/セリフ、ログイン/登録のテスト、画面の流れの E2E テスト）です。

### Hooks（手元の自動チェックと歯止め）

Hooks は、Claude Code の操作の前後に、決めておいたスクリプトを自動で動かす仕組みです（設定は `.claude/settings.json`、スクリプトは `.claude/hooks/`）。

| いつ | 何をする | 失敗したら |
|---|---|---|
| コマンドを実行する前 | main への push、force push、強制的な巻き戻し、全ファイルの一括 add、`.env` の表示を止める | 実行させず、理由を AI に返す |
| ファイルを開く・書く前 | `.env` ファイルを止める | 同上 |
| フロントのファイルを書いた後 | そのファイルだけ ESLint にかける | エラーを AI に返し、その場で直させる |
| 作業を終えようとしたとき | フロントに変更があれば、テストを実行する | 作業を続けさせ、直させる（1回だけ。無限に繰り返さない） |

**工夫したこと**：入れる前に、「止めるべきコマンド」と「通すべきコマンド」を並べて判定を試し、わざとエラーのあるファイルと、わざと失敗するテストで「本当に止まるか」を確かめました（[05](05-testing.md) の「テストのテスト」と同じ考え方）。バックエンドのテストは MySQL が必要で時間もかかるため、手元の自動実行には入れず、CI に任せています。

**つまずき（止めすぎ）**：入れた直後、AI がドキュメントを書き換えるコマンドが止められました。書き込む**文章の中に**、止める対象のコマンド名がそのまま含まれていたためです。判定を「コマンドの先頭（行の頭や `;` `&&` `|` の直後）にあるときだけ」に絞り、文章の中の文字列では止まらないことを、試験用の24件で確かめました。歯止めは**止めなさすぎも、止めすぎも**問題になります。止めすぎると、使う人が歯止めを外したくなるからです。

## 学んだこと

- ループの価値は、**検証の質で決まります**。検証が甘ければ、ループは間違いを速く量産してしまいます。
- 「全部を一度に自動化する」より、**1つずつ導入して、理解してから次へ**進むほうが、結果的に安全でした。
- 最終判断（マージ、公開）は人間が持ちます。AIに任せるのは、「実装」と「検証の実行」です。
