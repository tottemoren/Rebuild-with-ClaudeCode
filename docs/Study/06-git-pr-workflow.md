# 06. Git / PR の運用

## 基本の流れ

```
mainから作業用ブランチを作る（feature/内容）
        ↓
変更してコミット
        ↓
ブランチをGitHubへpush
        ↓
GitHub上でPR（プルリクエスト）を作る
        ↓
CIが自動で実行される
        ↓
CIが成功していることを確認して、マージ（人間が判断）
        ↓
役目を終えたブランチを片づける
```

## 用語の整理

| 用語 | やさしい説明 |
|---|---|
| ブランチ | 本編（main）に影響を与えずに作業できる、**作業用の枝**。付箋のようなもの |
| コミット | 変更を、メッセージつきで記録すること |
| push | 手元のコミットを、GitHubに送ること |
| PR（プルリクエスト） | 「この作業ブランチを、mainに取り込んでください」というお願い。**取り込むかどうかを決める場**でもある |
| マージ | ブランチの内容を、mainに取り込むこと |
| `ff-only` | 履歴を書き換えず、**ブランチの位置を進めるだけ**のマージ方式 |

## このプロジェクトのルール

- ブランチ名は `feature/内容`（例：`feature/backend-ci`）
- mainには直接コミット・pushしない
- PRの作成とマージは、人間（開発者）がGitHub上で行う
- マージ前に、Frontend CI / Backend CI が成功していることを確認する
- 1つのブランチ・PRは、**1つの目的**に絞る
- コミットは、関係するファイルだけを**名前を指定して**加える（`git add -A` や `git add .` は使わない）

## 学んだこと

### 1. pushとPRは別のもの

ブランチをpushしただけでは、PRはできません。pushのあとに、GitHub上で「PRを作る」操作が別に必要です。PRができたら、**決定権は人間にある**（マージするかどうかを選べる）ことが、はっきりします。

### 2. 「マージした」の確認は、実際の状態で

「マージした」という報告と、実際のGitHubの状態が食い違うことがありました（まだ開いたままのPRがあった）。そのため、PRの状態をGitHubの公開APIで確認してから、次の作業に進むようにしました。**会話の上での認識だけで進めない**ことが、事故を防ぎます。

### 3. 同じファイルを別々のPRで変えない

CHANGELOGのように、複数のPRが同じファイルを編集すると、マージのときに衝突（コンフリクト）します。そのため、先のPRのマージを待ってから、次の変更を加えました。

### 4. 未コミットの変更を巻き込まない

作業中に、別の作業の未コミットの変更が残っていることがあります。`git add -A` を使うと、それも一緒にコミットされてしまいます。そのため、**ファイルを指定して加える**運用にしています。

### 5. mainにマージすると、本番に反映されることがある

`RebuildReact/` に変更が含まれるPRをマージすると、**フロントエンドの本番サイトが自動で更新されます**（[04. CIとGitHub Actions](04-ci-github-actions.md)参照）。作りかけの内容を含んだままマージすると、そのまま公開されます。マージ前に、PRに含まれる変更を確認します。

## ブランチの片づけ

マージ済みのブランチは、消して構いません。**内容はmainの履歴に残る**ので、失われません。

| 場所 | 消し方 |
|---|---|
| ローカル（自分のパソコン） | `git branch -d ブランチ名`（マージ済みでないと拒否してくれる、安全な方式） |
| GitHub | ブランチ一覧のゴミ箱アイコン。または、設定で「マージ後に自動削除」をオンにする |

ローカルとGitHubは**別の場所**なので、片方を消しても、もう片方は消えません。

消さずに溜めると、一覧が見づらくなり、古いブランチから作業を始める間違いも起きやすくなります。
