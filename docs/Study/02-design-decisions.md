# 02. 設計判断と理由

設計書（`docs/01〜05`）には「何を決めたか」が書かれています。このノートでは、**検討した選択肢と、そう決めた理由**を整理します。

> **注意**：設計書には「目標とする設計」が含まれ、現在の実装と異なる部分があります（例：JWT認証・S3保存は目標で、現状は未実装）。食い違いがある場合は、実装が正です。詳しくは [api-list.md](../05-api/api-list.md) の「現行実装との主な差分」を参照してください。

## 判断の一覧

| # | テーマ | 決めたこと |
|---|---|---|
| 1 | 認証 | JWTトークン認証を導入する（現状は未実装） |
| 2 | イラスト素材の保存 | 目標はS3。v1の簡易版としてローカルディスクに保存 |
| 3 | 招待コード | 開発段階だけの暫定措置にする |
| 4 | 漫画データの持ち方 | 1枚の合成画像ではなく、座標つきの構造化データで持つ |
| 5 | DBの正規化 | ジャンルは別テーブルに分け、外部キー制約をつける |
| 6 | ページの概念 | `manga_pages` を新設し、コマとセリフを紐づける |
| 7 | セリフの座標 | 別テーブルに分けず、`dialogues` に直接持つ |
| 8 | 完成作品の扱い | v1は、見開きをPNGでダウンロードできるだけにする |
| 9 | 図の描き方 | drawioではなく、Mermaid記法を使う |

## 1. 認証：JWT

**現状**：ログイン情報を `localStorage` に保存しているだけで、バックエンドの全APIが誰でも使える状態（`permitAll`）です。

**選択肢**：
- A. このまま（簡単だが、他人のデータを見られる）
- B. JWTトークン認証を導入する
- C. セッション認証にする

**決めたこと**：B。フロントとバックを分離した構成と相性がよく、APIごとに「誰のデータか」を確認できるからです。

**学んだこと**：認証がないと、`userId` をURLで指定するだけで他人のデータが取れます。設計の段階で、この「認可の不備」を洗い出せました。

## 2. 素材の保存：S3（目標）とローカル（v1）

**選択肢**：
- A. サーバーのディスクに保存する
- B. S3に保存し、ブラウザから署名付きURLで直接アップロードする

**決めたこと**：目標はB。サーバーを経由しないので負荷が小さく、サーバーを入れ替えても画像が消えないからです。ただし、まず動くものを作るため、v1の簡易版ではAを使っています（`file.materials-upload-dir` の設定で保存先を切り替え可能）。

**学んだこと**：Dockerで動かしている間は、ボリューム設定がないとコンテナの再作成で画像が消えます。実際に、アップロードした画像が消える問題が起きたため、`compose.yml` にボリュームの設定を追加しました（[08. つまずきと解決](08-troubleshooting.md)参照）。

## 3. 招待コード：暫定措置

**現状**：バックエンドのコードに固定の文字列が書かれています。

**決めたこと**：開発段階限定の暫定措置とし、正式リリース時に廃止します。コードに固定値を書くのは、公開リポジトリでは特に避けたい形なので、「暫定」と明記して残しました。

## 4. 漫画データ：合成画像か、構造化データか

**選択肢**：
- A. 完成した漫画を、1枚の合成画像として保存する
- B. 素材の位置・大きさなどの座標を、構造化データとして保存する

| 観点 | A. 合成画像 | B. 構造化データ |
|---|---|---|
| 編集のしやすさ | 後から直せない | 素材を差し替え・移動できる |
| 素材の再利用 | 難しい | 同じ素材から何度でも作れる |
| 配信 | 画像1枚で簡単 | 描画の処理が必要 |

**決めたこと**：B。「同じイラストを使って何度でも漫画を作れる」というアプリの目的に合うからです。

## 5. DB：正規化と外部キー

設計の過程で、次の問題を見つけました。

| 問題 | 対応 |
|---|---|
| `memos` に `user_id` がなく、全ユーザーでメモが共有される | `user_id` を追加 |
| ジャンルが1つの文字列（画面では最大3つ） | `genres` と `story_genres`（中間テーブル）に分ける |
| メモの縦書き・横書きの区別がない | `writing_direction` を追加 |
| テーブル間の外部キー制約がない | 関連する全カラムに外部キー制約を追加 |
| コマ画像が単なるパス文字列 | `materials` への外部キー（`material_id`）に変更 |

**学んだこと**：外部キー制約は、「存在しない素材を指す」ような矛盾したデータを、DBの側で防いでくれます。**アプリのコードだけに頼らず、DBでも守る**のが安全です。

## 6〜7. ページの概念とセリフの座標

**気づいたこと**：コマ（`manga_panels`）が「ページ」という単位を持たず、ストーリーに直接ひもづいていました。セリフにも座標が必要だと分かり、設計の抜けが見つかりました。

**決めたこと**：
- `manga_pages` を新設し、コマとセリフの両方を `page_id` で紐づける
- セリフは、素材のように「マスタ＋配置」に分けず、`dialogues` に座標を直接持つ

**理由**：イラスト素材は何度も使い回しますが、セリフは使い回さないからです。**使い回すものだけを別テーブルに分ける**、という考え方です。

## 8. 完成作品の扱い

**決めたこと**：v1は、完成した漫画の見開き（隣り合う2ページ）をPNG画像として、端末にダウンロードできる機能だけにします。画像の生成はブラウザの中で完結させ、サーバーには保存しません。

**理由**：最初のリリースの範囲を絞ることで、実装と検証を小さく保てます。

## 9. 図の描き方：Mermaid

**選択肢**：drawio（図を描くアプリ）か、Mermaid（テキストで図を書く記法）。

**決めたこと**：システム構成図とER図は、Mermaidにしました。テキストなので、Gitで差分を確認でき、AIも編集しやすいからです。画面遷移図やワイヤーフレームは、画像（drawio）のままです。

## API設計で見つかった課題

既存の全Controllerを調べて、次の課題を見つけました。これらは、設計書の「現行実装との差分」として記録し、実装側は必要に応じて直す方針です。

- `/api` が付くエンドポイントと、付かないものが混在している
- メモのAPIが汎用のControllerに直接書かれ、Service層を通っていない
- 全ユーザーのデータを返すAPI、任意のIDで他人の情報が取れるAPIがある（認可の不備）
- エラーの返し方が、文字列とJSONで不統一

**学んだこと**：コードを書く前に、「現状の調査 → 課題の洗い出し → 目標の設計」の順で整理すると、設計書が単なる理想ではなく、実際に直すべき点のリストにもなります。
