# 05. テストの考え方

バックエンドのAPIテスト（[MemoApiTest](../../RebuildJava/src/test/java/com/example/demo/MemoApiTest.java)、[FolderApiTest](../../RebuildJava/src/test/java/com/example/demo/FolderApiTest.java)）を例に、テストの書き方と考え方を整理します。

## 何をテストしているのか

| テスト | 検証していること |
|---|---|
| メモAPI（3件） | 作成すると一覧に出る／更新すると内容が書き換わる（新規作成にならない）／削除すると一覧から消える |
| フォルダ/素材API（6件） | フォルダは作った本人の一覧にだけ出る／空のフォルダは削除できる／素材が残るフォルダは削除できない（409）／アップロードしたファイルが保存され、一覧に出る／空ファイルは拒否される（400）／素材を削除すると一覧から消える |
| コマ配置API（4件） | 保存した配置を読み込むと元に戻る／重なり順の小さい順に並ぶ／もう一度保存すると置き換わる／別のストーリーと混ざらない |
| アップロード画像の読み込み許可（4件） | フロントの配信元（開発・本番）からは許可される／登録していないサイトは拒否される／読み込み以外の操作は拒否される |
| `contextLoads`（1件） | アプリがエラーなく起動できる |

合計10件です。実際にHTTPのリクエストを送って、レスポンスの内容を確認する形式です。

## 使っている道具

| 道具 | 役割 |
|---|---|
| `@SpringBootTest` | アプリ全体をテスト用に起動する。DBにも実際に接続する |
| `MockMvc` | HTTPリクエストを疑似的に送る（実際にネットワークは使わない） |
| `@Transactional` | テストごとに、DBへの変更を**自動で巻き戻す**。データが残らず、何度実行しても同じ結果になる |
| `@TempDir` | テストが終わると自動で消える一時フォルダ |
| `@DynamicPropertySource` | アプリの設定を、テスト中だけ差し替える |
| `jsonPath` | レスポンスのJSONから、特定の値を取り出して確認する |

## 工夫したポイント

### 1. 実データに触れない

**DBの変更**：`@Transactional` により、テストが終わると巻き戻されます。

**ファイルの変更**：ところが、`@Transactional` は**ファイルの書き込みを巻き戻せません**。素材のアップロードは実際にファイルを書くため、`@TempDir` と `@DynamicPropertySource` で、保存先をテスト中だけ一時フォルダに差し替えました。これで、実際のアップロードデータ（`RebuildJava/uploads/`）は汚れません。

### 2. DBの元データと混ざらない

DBには、すでに実際のデータが入っています。テストの結果と混ざらないよう、**テスト専用の目印**（専用の題名、専用の `userId`）を使い、その目印で絞り込んで検証しています。

### 3. 「作成」だけでなく「その後の状態」を確認する

「作成APIが200を返した」だけでは、本当に保存されたかは分かりません。作成したあとに、一覧APIで**実際に表示される**ところまで確認しています。

### 4. テストを先に書いて、不具合を確かめてから直す

コマ配置APIの不具合では、直す前にテスト（4件）を書き、**修正前のコードで4件とも失敗する**ことを確かめました。失敗の内容（エラーの種類）から、推測していた3つの原因のうち2つが本当で、1つ（JSONでの項目名）は思い込みだったと分かりました。思い込みの部分は直さずに済みました。

**学んだこと**：コードを読んだだけの推測は外れることがあります。**先にテストで「再現」してから直す**と、直すべき場所だけを直せます。

### 5. `@Transactional` がテストの見落としを生むことがある

テストに `@Transactional` を付けると、テスト全体が1つのトランザクションの中で動きます。すると、**本体の処理にトランザクションの設定がなくても、テストの中では動いてしまいます**。コマ配置の「2回目以降の保存が失敗する」不具合は、まさにこれで、他のテストと同じ書き方では見つけられませんでした。

そこで、コマ配置のテストは `@Transactional` を付けずに書き、代わりに**テスト専用のストーリーID**（実際には使われない大きな番号）を使って、テストのたびに自分で後片付けするようにしました。

**学んだこと**：便利な道具は、**本番と違う条件を作ってしまう**ことがあります。テストが「本番と同じ条件」で動いているかを意識する。

### 6. 実データに触れずに確かめる工夫

- **CORSのテスト**：ブラウザが本番の読み込みの前に送る「確認の問い合わせ」（OPTIONS）で、許可の返事が付くかを確かめました。実際の画像ファイル（`uploads/` の実データ）を用意する必要がありません。
- **フロントの画像読み込みのテスト**：テスト用の環境（jsdom）は実際には画像を読み込まないので、`Image` を偽物に差し替え、「許可を求める読み込み方（`crossOrigin`）が、読み込み開始より前に設定されているか」だけを記録して確かめました。

## テストのテスト：ミューテーション確認

テストは「書いた」だけでは安心できません。**本体のコードが壊れたときに、本当に失敗するか**が大切です。

**やり方**：本体のコードを**わざと壊して**、テストを実行します。

| 壊した箇所 | 期待どおり失敗したテスト |
|---|---|
| 409を返す判定を無効化 | 「素材が残るフォルダは削除できない」 |
| ユーザーでの絞り込みを、全件取得に変更 | 「作った本人の一覧にだけ出る」 |
| アップロードしたファイルを、別の名前で保存 | 「ファイルが保存される」 |

| `/uploads/**` の読み込み許可を無効化 | 「フロントの配信元からは許可される」など4件（10月13日） |
| 画像を「許可を求める読み込み方」にする1行を削除 | 「許可（CORS）付きで画像を読み込む」（10月13日） |

壊した箇所と関係ないテストは、成功のままでした。確認が終わったら、コードは元に戻しました（差分が残らないことも確認）。

**学んだこと**：テストが緑でも、「何も確認していないテスト」の可能性があります。AIがテストを書くときこそ、この確認が大切です。

## つまずいたこと：Spring Boot 4 での変更

`@AutoConfigureMockMvc` が見つからず、コンパイルエラーになりました。Spring Boot 4 では、テスト用の部品が機能ごとに別のパッケージに分かれたためです。

- パッケージ：`org.springframework.boot.webmvc.test.autoconfigure`
- 追加が必要な依存：`spring-boot-starter-webmvc-test`（[build.gradle](../../RebuildJava/build.gradle)）

**学んだこと**：新しいバージョンでは、古い情報（以前の記事やAIの記憶）の通りに書いても動かないことがあります。エラーメッセージを手がかりに、確認することが大切です。
